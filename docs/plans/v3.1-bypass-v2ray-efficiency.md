## 1. Domestic bypass (Iranian sites leave through the non-VPN uplink)

### 1a. What Android allows

APIs (minSdk is 24, `android/app/build.gradle:16`):

| Need | API | Level |
| --- | --- | --- |
| Find a non-VPN internet network | `ConnectivityManager.registerNetworkCallback(NetworkRequest.Builder().addCapability(NET_CAPABILITY_INTERNET).addCapability(NET_CAPABILITY_NOT_VPN).build(), cb)` (a `NetworkRequest.Builder` already includes `NOT_VPN` by default) | 21 |
| Put one socket on that network | `Network.bindSocket(Socket)` / `bindSocket(DatagramSocket)` / `bindSocket(FileDescriptor)` (the last one for the ICMP ping fd) | 22-23 |
| DNS on that network | `DnsResolver.rawQuery(network, …)` (pass the `Network` instead of `null`) | 29 |
| DNS fallback below 29 | `Network.getAllByName(host)` fed into `MiniDns.answer(query, resolve)` (`MiniDns.kt:37` already takes a resolver lambda) | 21 |
| Detect "who is default" | `cm.activeNetwork` (per UID) + `NetworkCapabilities.hasTransport(TRANSPORT_VPN)` | 23 |

`ACCESS_NETWORK_STATE` is already declared (manifest). Only listening is needed, not
`requestNetwork`, so `CHANGE_NETWORK_STATE` is not required for the basic case. If the owner wants
"bypass through mobile data while the default is Wi-Fi", that needs `requestNetwork(TRANSPORT_CELLULAR)`
plus `CHANGE_NETWORK_STATE` (normal permission) and keeps the radio up: out of scope for slice 1.

**The hard constraint (decides feasibility on each phone):** whether an app that is *inside* the VPN
may bind to the underlying network depends on the VPN app.
- `VpnService.Builder.allowBypass()` not called (the Android default): apps "cannot side-step the
  VPN"; `bindSocket` to the underlying network is refused (typically `EPERM`) *(unverified per
  VPN app; the API contract says so)*. DNS on that network is expected to fail the same way
  *(unverified)*.
- `allowBypass()` called: `bindSocket` works. Which of v2rayNG, sing-box (SFA), Hiddify, NekoBox,
  WireGuard, OpenVPN call it is not known here *(unverified; must be tested per app)*.
- Always-on VPN with "Block connections without VPN" (lockdown): bypass is impossible, by design.
- PdaNext excluded from the VPN in the VPN app's per-app list: everything is already direct; the
  bypass list is moot (and the PC is not on the VPN at all; see 2A for detecting this).

So the feature must **probe** at runtime: on link attach and on every network change, try
`network.bindSocket(probeSocket)` on the chosen non-VPN network and report the result in
`/status` (`"directPath": "ok" | "blocked-by-vpn" | "none"`).

**No non-VPN network** cases:
- Wi-Fi only phone with VPN up: the non-VPN network is the Wi-Fi; direct traffic leaves with the
  Wi-Fi ISP's IP. If that ISP is domestic, the goal is met.
- VPN down: the default network is already non-VPN, everything is direct; the list has no effect.
- Callback reports no `NOT_VPN` internet network, or the probe fails: fall back. Decision needed
  (section 6b, D2): send listed hosts through the VPN (site may refuse a foreign IP) or block them
  (fail closed). Recommendation: through the VPN, with a visible warning on both UIs.

A zero-code alternative the owner should know about ("option 0"): v2ray-family apps have their own
"direct" routing rules (geoip:ir / geosite:category-ir and custom domain lists). PdaNext's flows are
app sockets, so those rules already apply to them: IP rules always, domain rules when the VPN app
sniffs TLS SNI / HTTP Host (on by default in v2rayNG *(unverified)*). If the owner already runs
v2rayNG with "bypass Iran" routing, the PC already gets domestic bypass today. Building it into
PdaNext is still worth it because it works with any VPN that allows bypass (WireGuard, OpenVPN,
commercial VPNs) and the list is edited from the laptop.

### 1b. How the router decides per flow

The router sees every name the PC resolves, because the PC's only DNS server is the gateway
(`NetConfig.cs:30`) and the NRPT rule sends all namespaces there (`NetConfig.cs:32-36`).

Options:
1. **By name (DNS-learned)**. In `Router.kt:103-111`, parse the question name (already done at
   `:104`). If the name matches the list, resolve it with the direct resolver, parse the A records in
   the answer (new parser; `MiniDns` only builds answers today), and record `ip -> (expiry, name)` in
   a `DirectMap`. On SYN (`Router.kt:187`), UDP flow creation (`:161`) and ICMP (`:143`), if the
   destination is in the map, the socket is bound to the direct network.
   - Pros: exact intent (the list is names); domestic geo-DNS returns the domestic answer, because
     the query itself goes out the domestic path.
   - Cons: blind when the PC resolves names some other way (browser DNS-over-HTTPS, hosts file, NRPT
     disabled, DNS cached before the list changed).
2. **By destination IP/CIDR**. A list of prefixes (manual entries, or an Iranian IP list from RIPE
   delegated stats). Lookup per new flow.
   - Pros: independent of DNS; catches DoH users and hard-coded IPs.
   - Cons: a full IR GeoIP list is large and goes stale; it routes *every* domestic-hosted destination
     direct, not just the owner's list (this may or may not be wanted).
3. **Both**: name-learned IPs OR manual CIDR entries. Recommended. A bundled country GeoIP list is a
   separate decision (section 6b, D4); slice 1 accepts only CIDRs the owner writes in the list.

Expiry rule for learned IPs: Windows and browsers cache answers for at least their TTL and some apps
keep using an IP longer. Recommendation: `expiry = now + max(answerTTL, 10 min)`, refreshed every
time a new flow uses the entry, with an LRU cap (estimate: 10 000 entries is far above normal use).
Do not rewrite the TTL in the answer: the answer stays byte-for-byte what the resolver returned
(this keeps the "real DNS answers" property; no fake IPs).

CNAME chains: the decision is made on the **question** name; every A record in the answer section
(including those after a CNAME to a foreign CDN name) is mapped. The router must not cross-check the
CNAME target against the list.

Per-flow stickiness: the path is chosen once, when the socket is created. A TCP session keeps its
socket for life (`TcpSession.kt:81`), a UDP flow keeps its socket until idle (`UdpFlow.kt:11-12`).

### 1c. DNS path checks

- **The router sees the names**: yes when "Send all DNS to the phone" is on (default,
  `AppSettings.cs:21-24`, NRPT at `NetConfig.cs:32-36`). With it off, Windows' smart multi-homed
  resolution may also ask the DNS of Wi-Fi/Ethernet; those answers are never seen by the router, so
  their IPs go through the VPN (fail-safe direction, but the bypass silently misses). The PC UI should
  say "Domestic bypass needs 'Send all DNS to the phone'" when the box is unchecked.
- **AAAA/HTTPS withholding** (`Router.kt:105-106`, `RouterConfig.ipv4OnlyDns` `Router.kt:27`): keep it
  for listed names too. If listed names got AAAA answers, Windows would use its own IPv6 (Wi-Fi)
  around the phone (`windows-adapter-and-dns.md`, "IPv6 leaks"): the site would still see a domestic
  address, but it would be the *laptop's* network, not the phone's, which is not what the owner
  asked for. Withholding HTTPS records also means no `ipv4hint` addresses the router has not learned.
  No change needed; the existing check runs before the bypass decision.
- **Browser DoH**: Chrome's automatic mode only upgrades when the system resolver is a known DoH
  provider; 192.168.42.1 is not, so it stays on system DNS *(unverified per browser version)*. A
  user-configured "Secure DNS" (Chrome/Edge custom provider, Firefox TRR) hides names from the
  router: listed sites then go through the VPN. Mitigation: CIDR entries; a note in the UI.
- **Direct DNS failure**: if the direct resolver fails, answer from the VPN resolver and do **not**
  map the IPs (the flow then goes via VPN, consistent with D2).
- **DNS privacy**: only listed names are sent to the carrier's resolver; all others keep using the
  default (VPN) resolver exactly as today.

### 1d. List format and matching

Input: one entry per line, UTF-8 text; `#` starts a comment; blank lines ignored. Each line is one of:

| Line | Becomes |
| --- | --- |
| `https://www.example.ir/path?q=1#x` | host `example.ir` (scheme, userinfo, port, path, query, fragment dropped; leading `www.` stripped) |
| `www.example.ir` | `example.ir` |
| `shop.example.ir` | `shop.example.ir` (only that subtree) |
| `*.example.ir` or `.example.ir` | `example.ir` |
| `ایران.ir` (IDN) | punycode via `IDN.toASCII` / `IdnMapping` |
| `ir` | every `.ir` name (offer as a checkbox "all .ir domains" rather than a magic line) |
| `185.143.232.0/22`, `2.144.0.1` | IP rule (IPv4 only; IPv6 is not routed through the phone) |

Normalisation: lowercase, strip a trailing dot, reject anything that is not a valid hostname or CIDR
and report the line number. Strip `www.` because owners paste browser URLs and sites serve both
`www.x` and `x`; the suffix rule then covers both.

Matching: **label-boundary suffix match**. `example.ir` matches `example.ir` and `a.b.example.ir`, never
`badexample.ir`. Implementation: a `HashSet<String>`; for a query name, test the name, then drop the
leftmost label and repeat (O(labels)). Parsing (URL → host) belongs to the PC side, where the list is
edited; the phone re-validates and uses only the normalised form.

Known gap to tell the owner: domestic sites load assets from other domains (static/CDN hosts). If
those are geo-checked too, the owner must add them; the PC log should list "names resolved while a
listed site was loading" to help *(nice-to-have, not slice 1)*.

Where the list lives and how it travels: the PC owns it (`%LOCALAPPDATA%\PdaNext\domestic.txt`,
edited in the Windows app) and sends it to the phone after the link comes up. Two transport options:
- (i) `POST /policy` on the existing HTTP side of port 28080 (`RelayServer.kt:124-127` would accept
  `POST`; `serveHttp` `:137` reads a `Content-Length` body). PDNR stays at version 1. Recommended.
- (ii) PDNR version 2 with typed control frames. Today a version mismatch is a hard error on both
  sides (`RouterLink.kt:43`, `RouterLinkProtocol.cs` handshake), so this needs a negotiated upgrade.
  Not worth it for a list.

The phone keeps the last list in app-private storage so a reconnect does not depend on the push.
Status JSON gains `directPath`, `directFlows`, `directBytes` (additive; `FlatJson` on the PC ignores
unknown keys, `PhoneStatus.cs:64-80`).

Security note (pre-existing, gets more important here): port 28080 is bound to the phone's loopback
(`RelayServer.kt:33`), so **any app on the phone** can connect, open a PDNR link, read `/status`, and
with (i) also rewrite the list. Slice 1 should require a per-install token for `POST` (the PC passes
it once with `am start … --es token`, `Bridge.cs:205`; the phone stores it). Item 2C cannot ship
without this.

### 1e. Edge cases

| Case | Behaviour with the recommended design | Mitigation |
| --- | --- | --- |
| Shared CDN IP (a listed name and a foreign name resolve to the same IP, e.g. Cloudflare) | After the listed name is resolved, the foreign site's flows to that IP also go direct for the entry's lifetime: the foreign site sees the domestic IP, and if it is filtered in Iran it may fail | Track all names seen per IP; if an IP was also returned for an unlisted name within its TTL, mark it "shared" and log it. Real fix (later slice): for TCP to a shared IP, read the TLS SNI / HTTP Host before connecting. That needs the SYN-ACK before `connect()` (today the router connects first and answers RST on failure, `TcpSession.kt:59-75`), so it changes "connection refused" semantics for those flows only. Not slice 1. Decision D5 picks the default winner. |
| Listed site resolves to foreign IPs (hosted abroad) | Goes direct anyway; the site sees the domestic IP, which is the intent | none needed |
| Domestic site uses geo-DNS | Direct resolver returns the domestic answer | this is why listed names must be resolved on the direct path |
| QUIC / HTTP/3 (UDP 443) | `UdpFlow` socket is bound like TCP, so QUIC goes direct too | must be in slice 1, or browsers using QUIC would mix paths |
| ICMP ping to a listed host | Bind the ping fd (`bindSocket(FileDescriptor)`) | cheap; include |
| Flows already open when the list changes | Keep their path (stickiness). PC flushes its DNS cache after sending the list (`ipconfig /flushdns`, as `NetConfig.cs:37` already does) so new lookups are seen | optional "apply now": abort affected TCP sessions with RST (`Router.tcp` map, `TcpSession.abort`) so apps reconnect |
| Uplink changes (Wi-Fi ↔ mobile) mid-flow | Direct sockets on the lost network die; apps reconnect; new flows take the new direct network | `NetworkCallback.onLost` clears the cached `Network` |
| Phone VPN reconnects | Default-path flows break today already; no new behaviour | none |
| DNS answer arrives after the PC already connected (race) | Not possible: the PC connects only after receiving the answer, and the map is written before the answer is sent | write map, then `send` |

### 1f. Recommended design and smallest first slice

Design: name-learned IPs + manual CIDR entries; direct DNS for listed names; per-flow binding at
the three socket-creation points; runtime probe of the direct path; fall back to VPN with a warning;
list owned by the PC, pushed with an authenticated `POST /policy`.

Core changes (platform-neutral, testable on Linux):
- `RouterPlatform` gains `resolveDnsDirect(query): ByteArray?`, `bindDirect(socket: Socket)`,
  `bindDirect(socket: DatagramSocket)`, `pingDirect(...)`, `directAvailable(): Boolean`.
- New `DomesticPolicy` (suffix set, CIDR list, `DirectMap` with expiry/LRU, DNS answer A-record
  parser).
- Hooks: `Router.kt:103-111` (choose resolver, learn IPs), `TcpSession.kt:60-62` (bind before
  connect), `UdpFlow.kt:11` (bind before connect), `Router.kt:143` (ping path).
- `RelayServer`: `POST /policy` with token; status fields.
- `JvmRouterPlatform`: `bindDirect` = bind to a configured local source address (lets the netns test
  emulate a second uplink with policy routing).

Android: `DirectNetworkTracker` (NetworkCallback, probe), `AndroidRouterPlatform` implements the new
methods with `Network.bindSocket` and `rawQuery(network, …)`.

Windows: "Domestic sites" text box (or file + "Edit" button), URL → host normaliser with unit tests in
`windows/tests`, push after `StartTunnel` (`Bridge.cs:172`), status line "Direct path: OK / blocked by
the phone's VPN / none".

**Smallest slice that proves the idea:** core + Android, TCP + UDP + DNS by name only (no CIDR, no
shared-IP detection, no "apply now"), list pushed by the PC on connect, probe + status field, one new
e2e check. Size **M**. CIDR entries and shared-IP logging are a follow-up **S**; SNI sniffing is **L**
and optional.

## 2. V2ray-style apps

### Facts that constrain every option

- Android runs **one** `VpnService` at a time. A second app calling `VpnService.prepare` takes over
  and the first is revoked. PdaNext is not a VpnService today and should not become one.
- PdaNext's router sockets are already inside the phone's VPN (unless PdaNext is excluded): with
  v2rayNG/Xray/sing-box running, the PC **already** goes through v2ray. This is the main finding: the
  common case needs no v2ray code at all.
- `VpnService.protect(socket)` (keep a socket out of the VPN) is available **only to the VPN app
  itself**, not to PdaNext. PdaNext can leave the VPN only through `Network.bindSocket` on a
  bypassable VPN (section 1a) or by being excluded in the VPN app's per-app list.
- ICMP through a v2ray tun: tun2socks-style stacks either drop ICMP echo or answer it locally with a
  synthetic reply *(unverified per app/version)*. So the PC's "Internet ping" (`MainForm.cs:420`,
  pings 1.1.1.1) can show "timeout" or an unrealistically low RTT when the phone runs v2ray. That is a
  display issue, not a routing bug, and should be explained in the UI when a VPN is active.
- Fake-IP: some configs answer system DNS with addresses in `198.18.0.0/15`. PdaNext forwards the
  phone resolver's answers unchanged (`Router.kt:108`), so the PC would receive fake IPs. Routing still
  works (the router connects to 198.18.x.y, the VPN maps it back to the name), but it breaks the
  project's "no fake-IP visible to PC apps" property (`windows-adapter-and-dns.md`, Detectability)
  and it breaks domestic bypass (a fake IP cannot be reached on the direct path).

### Option A: keep the VPN app as is; detect, explain, warn

What it adds:
1. **VPN detection** already exists (`UplinkInfo.kt:34`, shown on PC at `MainForm.cs:372`).
2. **"PdaNext is excluded from the VPN"**: `cm.activeNetwork` is per UID. If some network in
   `cm.allNetworks` (or a `NetworkCallback` requesting `TRANSPORT_VPN` with `NOT_VPN` removed) has
   `TRANSPORT_VPN` but PdaNext's `activeNetwork` does not, PdaNext is excluded (or not included in an
   allow-list VPN). Status field `vpnExcluded: true`; PC shows "The phone's VPN is on, but PdaNext is
   excluded from it: the PC is NOT on the VPN". High value: today the PC shows "VPN: Off" while
   the phone shows the VPN key icon, with no explanation of why. This is the most likely
   misconfiguration *(detection method unverified on a real phone)*.
3. **Which app owns the VPN**: `NetworkCapabilities.getOwnerUid()` is redacted for other apps
   (returns `INVALID_UID`) on recent Android *(unverified)*. Do not promise the app name; show
   "a VPN" only.
4. **Fake-IP detection**: in the DNS path (`Router.kt:108`), count A records inside `198.18.0.0/15`
   (and `fc00::/18` if AAAA were ever allowed). Status `fakeIpAnswers: n`; PC warns "The phone's VPN
   answers DNS with fake IPs; turn off FakeDNS in the VPN app" (v2rayNG: "Enable fake DNS"; sing-box:
   `fakeip` DNS server). The router must **not** rewrite or re-resolve them (that would be a resolver
   of its own, and "fixing" fake IPs means implementing the VPN's routing); warn only.
5. **Exit IP**: a "Check exit IP" button (on demand, never polled) that makes the *phone* fetch a
   what-is-my-IP endpoint with a router-equivalent socket, and, with item 1, a second fetch on the
   direct path. Third-party endpoint choice is decision D8. Polling it would cost data and wake the
   radio; do not.

Size: **S** (status fields + PC labels) to **M** with the exit-IP button on both sides. Android
constraints: none beyond `ACCESS_NETWORK_STATE`. Secrets: none. UDP: whatever the VPN supports.
ICMP: as above. Rule change: **none**. This is pure observation.

### Option B: embed an Xray core in the phone app

Shape: a gomobile AAR (like v2rayNG's `libv2ray`), started inside `RelayService`. The router's flows
must be handed to it. Three ways:
- B1: Xray listens on a loopback SOCKS/dokodemo inbound and the router connects through it. This is
  literally a proxy hop inside the phone (not visible to PC apps, but it is a proxy).
- B2: gomobile binding that exposes `Dial(network, address)` returning a connection object; the
  router copies bytes between `TcpSession` and that object (no listening port). Per-chunk JNI/gomobile
  copies on every byte *(cost unmeasured)*.
- B3: feed the PC's raw IP packets into a Go tun stack (tun2socks) inside the AAR. This replaces the
  Kotlin router and its tested behaviour (ping, RST, half-close), i.e. a rewrite.

Constraints:
- The Xray outbound's own server connection is an ordinary socket of PdaNext. If the phone also runs
  a VPN app, it goes into that VPN (double tunnel) unless PdaNext is excluded there. The clean
  setup is: phone VPN app for the phone with PdaNext excluded, PdaNext's Xray for the PC.
  PdaNext cannot call `protect()`.
- Size: an Xray AAR adds tens of MB per ABI to the APK (**estimate**; v2rayNG's APKs are split per ABI
  for this reason). CI builds the APK (`dl.google.com` blocked in cloud sessions) and gomobile needs the
  NDK there.
- UDP: depends on the outbound. VLESS/VMess/Trojan carry UDP (XUDP / UDP-over-stream), Shadowsocks
  needs server UDP, HTTP outbound has none *(per protocol, unverified per server)*. `UdpFlow` must fail
  fast (ICMP unreachable, `Router.kt:164`) when the outbound has no UDP.
- ICMP: Xray does not carry ICMP. `Router.handleIcmp` would have to either reply "unreachable" or ping
  outside the tunnel (misleading: the ping would not measure the tunnel). Owner's "ping the internet"
  mental model breaks.
- DNS: must go through the outbound (Xray DNS with an outbound tag, no fakedns), otherwise names
  leak to the carrier. Xray can then route by domain only if it is told the name: the router does not
  have it (PC connects by IP) unless the DNS-learned map from item 1 is passed along with each dial.
- Secrets: configs hold UUIDs, passwords, private keys (Reality), server addresses. Requirements:
  stored only encrypted (AES-GCM with a non-exportable Android Keystore key; app-private file;
  `allowBackup="false"` is already set in the manifest), never in logs (`RelayService` logs every
  router message to logcat via `Log.d`, `RelayService.kt:74`; config parsing errors must be redacted),
  never returned by any HTTP endpoint (write-only; GET returns a redacted summary), never in status JSON.
- Battery/CPU: a second user-space crypto stack per byte on the phone (**estimate**: noticeably more CPU
  than the plain router; would undercut item 4).
- Rule: B1 is a proxy and needs the owner to change the rule. B2/B3 are not a "proxy mode" in the
  sense the rule was written (a PC-visible system proxy or a SOCKS hop with fake-IP), but they do make
  PdaNext a proxy *client*, which the rule's spirit ("PdaNext is a router, not a proxy") excludes. My
  reading: **B needs an explicit owner amendment** such as "PdaNext may embed a VPN/proxy *outbound*
  on the phone; the PC must still see only an adapter, real DNS answers, and no proxy settings".

Size: **L** (B2), **XL** (B3).

### Option C: config manager driven from the laptop

The PC edits/imports configs (share links `vless://…`, subscription URLs, JSON) and sends them to
the phone, which validates, stores encrypted, and applies them to B. It is useful only together with
B (a config manager for *another* app is not possible: v2rayNG/sing-box do not offer a write API to
third-party apps; at most PdaNext could open an import intent/QR, which is not "editing"
*(unverified per app)*).

Extra requirements over B: authenticated control channel (token from section 1d; any phone app can
reach 28080 today), PC-side storage encrypted with DPAPI (`ProtectedData`, CurrentUser, available in
.NET Framework 4.8), no secret in the Windows log window (`MainForm` log) or `AppSettings` registry
values, subscription fetch path choice (fetching a subscription over the very tunnel it configures can
deadlock: fetch direct or via the phone's VPN), and a rollback if a new config does not connect.

Size: **L** on top of B. Rule: same amendment as B.

### Recommendation for item 2

Do **Option A** now (S/M): it covers what the owner actually runs (a VPN app on the phone), needs no
rule change, and it surfaces the two misconfigurations that silently break the product (PdaNext
excluded from the VPN; fake-IP DNS). Tell the owner that the PC already uses v2ray whenever the phone
does. Do not start B or C unless the owner (1) amends the rule in writing, and (2) has a concrete
need that A cannot meet, e.g. "the phone itself must not use the VPN while the PC must", or "a
different server for the PC". If that happens, B2 + C is the shape, after a security pass on the
loopback control port.

## 3. TTL and carrier counting

### 3a. Is there any TTL/hop-limit change left in the code?

`grep -rniE "hoplimit|defaultcurhoplimit|ttl|ipconfig"` over `*.cs *.kt *.wxs *.ps1 *.sh *.py`:
- No `netsh … defaultcurhoplimit`, no hop-limit setting anywhere in `windows/` or the installer
  (`windows/installer/PdaNext.wxs` custom actions only stop the app, remove the logon task and the NRPT
  rule, lines 85-95).
- `ipconfig` is used only for `/flushdns` (`NetConfig.cs:37`, `:46`).
- `Packets.kt:133` `DEFAULT_TTL = 64` and `Packets.kt:207/219`: TTL of packets the router builds
  **towards the PC** over the USB link; `Router.kt:144` uses 56 for ping replies so they look like they
  came from a few hops away. These never leave the USB link.
- `Packets.kt:30` parses the PC's TTL into `IpPacket.ttl`; nothing reads it (no other `.ttl` use in
  `core/` or `android/`).
- `MiniDns.kt:72`: DNS record TTL (60 s) in fallback answers, unrelated.
- The only historical TTL change was in v2 (`docs/HEALTH-CHECK.md:51-54`: `defaultcurhoplimit=65`, later
  forced to 128). Windows' default is 128, so a PC that ran v2 to completion is back to default; a PC
  where v2 crashed between the two steps could still be at 65 *(possible, not verified on the owner's
  PC)*.

### 3b. Can the carrier see the PC's TTL?

No. The PC's packets end at the phone's router: TCP is terminated (`TcpSession`), UDP payloads are
re-sent from a new socket (`UdpFlow.kt:24`), ICMP echo is re-originated by a ping socket
(`AndroidRouterPlatform.kt:55-67`). Every packet the carrier receives is built by the phone's kernel for
PdaNext's own sockets, with Android's TTL (64) and Android's TCP options (window scale, timestamps,
MSS of the phone's interface). With a VPN active, the carrier sees only the VPN's outer packets. The
PC's TTL, TCP fingerprint and IP ID never reach the carrier. Nothing to check or change; the rule
"never change the PC's global TTL" stays. Suggested small addition: a read-only check that shows a
warning if `netsh interface ipv4 show global` reports a non-default hop limit (a leftover from v2 or
another tethering tool), with the command to restore it for the user to run. PdaNext must not change it
itself.

Kernel tethering is not used, so Android's tethering entitlement check and the carrier's DUN APN never
apply either (`android-routing-and-vpn.md`).

### 3c. Can the traffic avoid being counted?

Honest answer: **no, not on mobile data.** The bytes PdaNext sends and receives are the phone's own
app traffic; the carrier counts every byte that crosses its network, exactly like a browser on the
phone. The design changes *which bucket* Android puts it in (PdaNext's UID, not "Tethering & hotspot"),
not whether the carrier bills it. A VPN adds its own overhead on top (**estimate**: a few percent to
~10 % depending on protocol and packet sizes).

What can legitimately reduce or change counting:
- **Wi-Fi uplink**: when the phone is on Wi-Fi, no carrier data is used. PdaNext already follows
  whatever uplink Android picks.
- **Domestic bundles** (Iranian carriers sell cheaper "domestic traffic" packages): these are
  classified by the carrier, usually by destination (domestic IPs/hosts) *(carrier-specific,
  unverified)*. Through a VPN to a foreign server, everything is international. **Item 1 helps here**:
  listed domestic sites leave on the direct path to domestic IPs, so they may be counted as domestic.
  This is a side effect to test, not a promise.
- **Zero-rated services** (carrier promotions for specific apps/sites): depend entirely on the
  carrier's classification (SNI/IP/DPI). Direct-path flows look the same as the phone's own traffic to
  those services; flows through the VPN never qualify.
- What PdaNext must not do: disguise traffic as zero-rated hosts (SNI/Host spoofing, domain fronting)
  to avoid billing. That is evading the carrier's billing, not a networking feature; it is out of scope.

What PdaNext can do: **show** counted bytes clearly. It already counts up/down (`RelayStats`, shown on the
PC at `MainForm.cs:382`). With item 1, split by path (`vpnBytes`, `directBytes`) and by uplink
(mobile/Wi-Fi), so the owner sees what went through the carrier and what was domestic. These counters
are payload bytes at the socket level; the carrier's number is higher (IP/TCP headers, VPN overhead,
retransmissions). Label it "approximate" in the UI.

Clear answer for the owner: the PC's TTL is irrelevant and is not touched; the carrier cannot tell the
traffic comes from a PC by TTL; but it will count all of it as the phone's data, and only Wi-Fi,
domestic bundles (with the bypass) or carrier zero-rating can change the cost.

Caveat worth stating: without a VPN, the carrier can still guess there is a PC behind the phone from
*content* (DNS names and TLS SNI such as Windows Update hosts). With a VPN, it sees only encrypted
volume. TTL is not the signal.

## 4. Efficiency audit

Goal: clearly better battery/CPU/wakeups than v3.0.0, without weakening (a) dead-link detection
(15 s keep-alive, 45 s read timeout: `RouterLink.kt:86-88`, `RouterTunnel.cs:38`, `:102-118`) and
(b) prompt teardown when the cable is pulled (`Bridge.cs:235-241`).

First step: **measure a baseline** on a real phone and PC (nothing has been measured). Phone:
`adb shell dumpsys batterystats --reset` then `dumpsys batterystats io.github.alimhbtwenty.pdanext`
after 30 min idle-connected and 30 min under load; wakelock time, CPU time, wakeups;
`dumpsys wifi` for the lock. PC: process CPU time of `PdaNext.exe` and count of `adb.exe` launches
(Process Monitor or `Get-Process` sampling) over 10 min idle. Without this, "clearly better" cannot be
claimed.
